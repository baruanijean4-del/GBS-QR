# Langues et vocabulaire métier

Quatre langues : **français, anglais, portugais, swahili**. Le vocabulaire
change aussi selon le **type d'établissement** (hôtel → « chambre »,
restaurant ou terrasse → « table », boutique ou pharmacie → « comptoir »,
billard → « billard »).

Trois couches, de la plus visible à la plus technique.

## 1. Les écrans : `src/i18n/{fr,en,pt,sw}.json`

- `t('cle.pointee', { variable })` partout dans les écrans. Repli : langue →
  anglais (pt) → français → la clé.
- Les quatre fichiers ont **exactement les mêmes clés** (test + `npm run i18n`).
- Aucun texte français en dur dans le JSX : `npm run i18n` échoue sinon
  (lancé aussi par la CI).
- Ajouter un texte : créer la clé dans les **quatre** fichiers.

## 2. Le vocabulaire métier : `t()` le fournit seul

Chaque écran déclare l'établissement affiché (`useEtablissementCourant`, déjà
appelé par `PorteRole` pour tous les espaces staff et par la vue client).
`t()` ajoute alors, selon son type (source : `TYPES_ETABLISSEMENT`,
`contracts/types.ts`) :

| Variable | Exemples |
|---|---|
| `{zone}` `{zones}` | table(s) · chambre(s) · comptoir(s) · billard(s) |
| `{Zone}` `{Zones}` | même mot, majuscule initiale |
| `{un}` `{le}` `{ce}` `{du}` `{au}` | articles accordés (fr, pt) : une table, un comptoir… ; swahili : `{ce}` = hii / hiki |

Exemples : `"Ajouter {un} {zone}"` → *Ajouter une chambre* (hôtel),
*Ajouter un comptoir* (boutique) ; `"{Zone} {numero}"` → *Table 3*.

Règles d'écriture :

- **Éviter les accords d'adjectifs** (« assignée ») : écrire « {Zone} {numero} :
  {nom} s'en occupe » plutôt que « {Zone} assigné(e) ».
- Pour une liste d'établissements de types différents (tableau du propriétaire,
  super-admin), passer le vocabulaire de chaque ligne :
  `t('cle', { zones: vocabulaireDe(langue, e.type, e.typesSecondaires).zones })`.
- Un établissement fusionné (plusieurs métiers) prend le vocabulaire de son
  type **principal**.

## 3. Les messages du serveur : `api/i18n/serveur.{en,pt,sw}.json`

Le code serveur reste écrit en français : `erreur("Code PIN incorrect.")`.
**Le gabarit français est la clé** du catalogue de chaque langue. Le client envoie
sa langue dans l'en-tête `x-lang` ; le serveur traduit :

- les erreurs tRPC (`errorFormatter`, `api/middleware.ts`) — saisie invalide
  (Zod) comprise ;
- les réponses d'erreur hors tRPC (`api/boot.ts`) ;
- les **alertes / notifications** envoyées dans le snapshot
  (`traduireAlertes`, `api/gbsSnapshot.ts`).

Variables : dans le code, `${x}` devient `{}` ; dans les catalogues elles sont
**numérotées** (`{1}`, `{2}`…) pour pouvoir changer l'ordre des mots.
Exemple : `"Stock insuffisant pour {}. Disponible : {}."` →
`"Not enough stock for {1}. Available: {2}."`.

**Ajouter un message d'erreur ou d'alerte** : l'écrire dans le code, puis ajouter
sa traduction dans les trois catalogues. Le test
`api/__tests__/messages-serveur.test.ts` lit le code source et échoue si un
message n'est pas traduit (ou si un catalogue contient une entrée orpheline).

Un message sans traduction retombe sur le français (jamais d'écran cassé).

## Ce qui reste en français

- le **journal d'audit** (`journaliser(...)`) : trace interne, non traduite ;
- les **exports CSV** du serveur (en-têtes de colonnes) ;
- le nom et la description du **manifeste PWA** (`public/manifest.webmanifest`,
  un manifeste est statique) ;
- le texte saisi par les utilisateurs (motifs, noms, produits).
